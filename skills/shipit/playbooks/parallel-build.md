### Parallel build

**You own the split, the reviews and the one PR.** Delegates write the slices. You review every diff, integrate every branch, and prove the whole. Nothing a delegate says counts until you've looked.

For a big build the user wants split ("in subagents", "in worktrees", "max 5 agents"), or a **Feature** whose throughput checkpoint shows three or more independent workstreams. Code-coupled work stays with one owner per **Feature**.

1. **Prove it splits.** Write the throughput checkpoint (Feature step 3, `~/.claude/skills/shipit/playbooks/feature.md`). Slices must touch disjoint files, or the overlap must be append-only (a changelog bullet, a registry entry). Shared types, schemas, tokens and primitives are a blocking phase. You or one owner land them on a base branch before fan-out (the **Separate Before Serializing Shared State** principle, `~/.claude/skills/shipit/principles/separate-before-serializing-shared-state.md`). If the split needs more than one serial phase, or most slices touch the same file, don't fan out. Run **Feature** with one owner.
2. **Write the slice table.** One row per slice with its id, scope (paths it owns and paths it must not touch), branch name, the check that says it's done (a command with a pass/fail result), the proof it owes, dependencies, and status. Publish it now as the status artifact. Inside berth, a CSV with the **berth-artifacts** skill (a `status` column colors the rows). Outside berth, the `Artifact` tool, or a markdown table you repost on each update.
3. **Write each brief consolidated.** A delegate gets everything it needs in one prompt: the original ask, every later directive from the user, the data shape and its organizing structure (the **Model the Domain** principle, `~/.claude/skills/shipit/principles/model-the-domain.md`), its scope and its do-not-touch list, the check, the proof it owes (`~/.claude/skills/shipit/references/proof-pack.md` rows that apply), the repo's rules file (AGENTS.md or CLAUDE.md), the saved memory lines from the project's memory that bear on the slice (rejections and constraints, quoted, since a delegate may not see them), and the router's path (`~/.claude/skills/shipit/SKILL.md`). It commits to its own branch. It doesn't open a PR, merge, rebase onto other slices, or touch another slice's files. Its last message is the report, with the branch, the commits, each check run and its output, its proof, and anything it couldn't do.
4. **Launch, capped.** At most 5 running at once, or the user's cap. Queue the rest and start the next as each one lands. With berth, a berth task per slice (`berthd task new <loc>/<slice> --agent claude --prompt "…"`, or the `berth_task_new` MCP tool). Each gets its own worktree, port and env, and reports back with a `<berth-notification>`. See the **berth-orchestrate** skill. Without berth, the Agent tool with `subagent_type: "shipit-agent"`, `isolation: "worktree"`, and the model and effort the Subagents section of the router sets. End your turn. Don't poll.
5. **Review each slice as it lands.** Read the full diff yourself (`git diff <base>...<branch>`). Check it stayed in scope. Run its check yourself (`berthd exec <loc>/<wt> -- <cmd>` in berth, else in its worktree). Look at its proof, every screenshot opened. Then mark the row accepted, or send it back. A fix round goes to a fresh delegate with the consolidated brief, the prior report, the branch, and your review notes. Resume the old delegate only when it holds state that is costly to move (uncommitted work, a running dev server). Update the status artifact on every change.
6. **Answer status from the table.** "How's it going?" gets the slice table: done, running, queued, blocked, with the artifact link. Silence from a delegate past its expected time is a status too. Check its state with `berthd sessions --json` (or the `berth_sessions` tool), or a short `berthd session wait NAME --timeout 90s --json`, then end the turn. Never block on `session wait` with its default timeout. Without berth, check the Agent notification. Say what you found.
7. **Integrate into one branch.** When every slice is accepted, use the repo's own integrate skill when it has one (`.claude/skills/integrate-branches/SKILL.md` or similar; read it and follow it). Otherwise, in a scratch worktree from the current `origin/main`, merge one branch at a time with `git merge --no-ff`, foundational slices first, UI last. Keep both intents in every conflict. Preview with `git merge-tree --write-tree origin/main <branch>`. Don't rebase delegates' branches.
8. **Check the whole.** Run the repo's full checks on the integrated tree from a clean install. Look for breaks that merged cleanly (one slice renames what another's test clicks). Run the specs of every area two slices both touched. A failure that belongs to one slice goes back to step 5 for that slice.
9. **Prove it.** Build the proof pack (`~/.claude/skills/shipit/references/proof-pack.md`) on the integrated branch, not per slice. Run **Design audit** (`~/.claude/skills/shipit/playbooks/design-audit.md`) for any UI the build added.
10. **Open one PR to main.** Run **Opening a PR** (`~/.claude/skills/shipit/playbooks/opening-a-pr.md`). One branch, one PR, base `main`. Never a stack of PRs, and never a PR based on another feature branch. The body lists the slices, the merge order, each conflict and how it was resolved, cross-slice fixes, and the check results. After it merges, clean up the slice branches and worktrees (**Worktree cleanup**, `~/.claude/skills/shipit/playbooks/worktree-cleanup.md`).

**Reply:** the slice table (final), what each slice built and what you changed in review, the merge order and conflicts, the checks on the integrated tree, the proof pack and PR links, and anything cut or deferred with the reason.
