### Autopilot-stack

**You own the stack, never the landing. Hand the operator one linear stack of base-chained PRs to review and land.** Run this playbook only when the user explicitly asked for a stack. **Autopilot-full** holds except for how verified work leaves. Each tick re-reads both playbooks from disk (`~/.claude/skills/shipit/playbooks/`), and this one wins where they differ.

1. **Run Autopilot-full's owners, minus the landing.** Owners report STACK-READY in place of merge-ready. They never rebase onto another branch, trunk included, and never retarget, merge, close a PR, or arm auto-merge, because the root owns the chain's topology and the operator owns the landing. An owner takes its parent's new tip only when you ask, by merging it into its own branch (`git merge origin/<parent-branch>`) and pushing. When an item depends on another, its owner branches from that item's branch, not from trunk. On berth, that owner's task starts from the parent's branch (`berthd task new <loc>/<name> --base <parent-branch> --agent claude --prompt "…"`).
2. **Give the topology one writer.** Owners push only their own branches and report each tip and its intended parent. Only you decide when a link moves, and only you retarget one, because two writers on one chain undo each other. You never push to an owner's branch. Append each clean PR in dependency order, with its base set to its parent's branch (`gh pr edit <pr> --base <parent-branch>`). Never require `gt`. To move a link onto its parent's new tip, tell its owner to merge the parent branch and push, resolving any conflict in its own slice. A rebase with `--force-with-lease` happens only on the owner's own branch, by the owner. If auto mode denies the force push, the owner stops and reports. Never retry it.
3. **Absorb drift at the root.** Until landing starts, apply Autopilot-full step 5's test to each link and have the owners update the chain bottom-up where it calls for one. Then apply the patch-id rule link by link, since a link's base is its parent.
4. **Deliver the chain, then keep your hands off it.** Each link carries its verdict in its PR. Once landing starts, nobody writes to the chain except the post-merge retarget that `~/.claude/skills/shipit/playbooks/shipping.md` sanctions, because a second writer breaks a landing in flight. A mid-landing problem goes through you to the operator, and any fix waits for the operator's go.
5. **Hand over the retarget rule with the chain.** Merged branches are not deleted in these repos, so GitHub does not retarget a link when its parent merges. A link merged while its base is still its parent's branch lands in a dead branch, not trunk. State it in the handover. After each lower PR merges, the next one is retargeted to trunk (`gh pr edit <pr> --base <trunk>`) and its patch moved onto trunk before it merges, per `~/.claude/skills/shipit/playbooks/shipping.md` step 4. If the operator asks you to land the stack, that is Shipping, and you do the retarget yourself.

**Choosing between the autopilots.** Autopilot-stack only when the user explicitly asked for a stack. Otherwise run Autopilot-full's owners as independent PRs off trunk. When the operator wants review before landing or withholds merge authority, those PRs stop at merge-ready. A PR that depends on another waits for its parent to merge, then branches from trunk.

**Evidence.** The stack is a table artifact, one row per link bottom to top: PR link, branch, base, head SHA, verdict and the SHA it covers, patch-id match after the last chain rebase. Rewrite it each tick (the **berth-artifacts** skill; outside berth, the `Artifact` tool or a markdown table).

**Reply:** catch the operator up per the **ketchup** skill, with links to the stack root and tip, a one-line verdict per link, the retarget rule for landing, the stack table, and anything parked or excluded with the reason.
