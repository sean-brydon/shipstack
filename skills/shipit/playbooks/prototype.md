### Prototype

**You own the design decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.**

The one playbook where the Laziness Protocol's "smallest change" and the verification bar invert. Speed over polish, code quality does not matter, no planning. The rigor is in picking the right design cheaply. Propose variations the user didn't ask for, throw an approach away and try another.

1. Scope the decision the prototype exists to make: which layout, which interaction, which density, or for an empirical fork which behavior, timing, or approach. No decision means no prototype. Route to Feature.
2. Gather references when the design space is open. Search for prior art, summarize a moodboard of themes, palettes, and layouts, let the user pick directions before building. Skip when the direction is set.
3. Build throwaway in an isolated scratch dir, separate from production source (the session's scratchpad directory when the system prompt names one). For a visual decision, vanilla HTML/CSS/JS or the lightest stack that renders the idea, CDN deps, a dev server with hot reload. For a behavioral or timing decision, the smallest script that exercises the question. No production framework, no tests, no abstractions. When the decision only makes sense inside the real app (it needs the app's data, routes, or components), sketch it on a throwaway branch in its own worktree instead. On berth, that is a berth task per variant (see the **berth-orchestrate** skill), each with its own dev server and port. Without berth, use the Agent tool with `isolation: "worktree"`. Never sketch in the user's checkout.
4. When comparing alternatives, build them behind one switcher (buttons or a keypress), each variant labeled. This is the **Exhaust the Design Space** principle (`~/.claude/skills/shipit/principles/exhaust-the-design-space.md`) made cheap. Variants in separate worktrees can't share a switcher, so label each one's page and compare them side by side.
5. Verify on the matching surface. For a visual decision, screenshot each variant via the control skill and drive the interaction. Inside berth, that is the **berth-browser** skill (`berthd browser shot`, `berthd browser resize phone` for a small-screen check). Without berth, the **claude-in-chrome** skill. For a behavioral or timing decision, observe the thing you are deciding by logging the timing, printing the output, or watching the render. The observation is the test here, not an assertion.
6. Put the prototype in front of the user. Inside berth, open it beside them with the **berth-preview** skill so they can flip the switcher themselves. Outside berth, a self-contained HTML sketch can go up as a private page with the `Artifact` tool (load the **artifact-design** skill first). For a timing or behavioral fork, chart or tabulate the observed numbers per variant with the **berth-artifacts** skill, or a markdown table outside berth.
7. Present alternatives, tradeoffs, and a recommendation. The output is the decision plus the throwaway artifact, not shippable code. Hand the chosen direction to **Feature** (or the **architect** skill, `~/.claude/skills/architect/SKILL.md`, for the shape) for the real build.

**Reply:** the variants explored, the evidence (screenshots for a visual decision, the observed output or timing for a behavioral one, as a table or chart when there are several numbers), tradeoffs, your recommendation, the preview or artifact link, and the scratch path or worktree. Say plainly that the prototype is throwaway.
