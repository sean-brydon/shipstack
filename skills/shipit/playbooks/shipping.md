### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

**Merged branches are not deleted in these repos.** GitHub retargets a child PR to trunk only when its parent's branch is deleted. Here the branch stays, so a stacked PR keeps its parent's merged branch as its base, and merging it lands the code in a dead branch, not trunk. Every merge below therefore checks the base first.

1. **Verify each PR independently before it lands.** The forge is GitHub through `gh`. Never require Graphite (`gt`). One verifier per PR runs the change the way a user would, parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR (`gh pr comment <pr> --body-file <verdict.md>`), with the head SHA it verified and its evidence (screenshots, command output). The verifier never checks out the head branch, because the PR's owner holds it. Each verifier is a helper on the `verification` role's model, in its own detached checkout of the head (`git worktree add --detach <path> origin/<head-branch>`). If an orchestration tool is present, it can instead give each verifier a task on its own branch from the head, with its own worktree, port, and dev server (see your adapter). The verifier drives a page on the real surface, with a visual diff against the base for anything that renders, and a CLI or TUI from the shell or a terminal multiplexer. For a page it can use the Playwright the project already has. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Run the verifier on a different model family from the author where the roster allows. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time, and only into trunk.** Always merge the run's lowest unmerged PR. Before the merge, read its base (`gh pr view <pr> --json baseRefName`). If the base is not trunk, do not merge. Its parent has merged and left its branch behind, so retarget it first (`gh pr edit <pr> --base <trunk>`), then bring trunk into its branch (`git merge origin/<trunk>`) and push, with no force push. The branch's owner does that update (message the owner, if another agent holds it), or you do it when the branch is yours. A rebase onto trunk with `--force-with-lease` happens only on the pusher's own branch. If the permission mode refuses it, stop and report. Don't retry. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Then wait for its checks. Merge with `gh pr merge <pr> --squash` once its checks pass, its verdict survives, and its base reads trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads `MERGED` with trunk as its base, not its parent's branch. A PR that reads merged into a parent branch landed in a dead branch. Report it at once, and land its patch on trunk through a new PR with a fresh verdict. Arm `--auto` only on a PR whose verdict covers its current head and whose base already reads trunk, because it lands whatever head is ready into whatever base it has. After each merge, retarget the next PR up to trunk the same way before anything else.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Watch the run with the queued watcher from `playbooks/babysit.md` (`watch-pr --queued-stack --stack-prs <bottom-to-top>`) as a background watcher, so each `ADVANCE` arrives as an event (see your adapter for how events reach you), until it reports `COMPLETE` at the ceiling. Re-arm it when it expires. A base you retarget to trunk after its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Evidence.** Keep one verdict table for the run and update it as each PR moves: PR link, head SHA, patch-id match, verdict, verifier (agent and model), evidence link, base at merge, merged state as read back. Make it a table artifact (a CSV with a `status` column, rewritten in place so it updates live) when the run spans more than a few PRs, else a markdown table in the reply. Name the commands the rows came from.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it (the read-back, with base `main` or trunk), and what the next gap needs. Link the verdict table.
