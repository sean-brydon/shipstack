### Visual parity

**You own pixel-exact equivalence. The baseline is the spec. You do not touch it.** Equivalence is verified by image diff, not by eye.

1. Establish the baseline first, before any migration: a visual regression harness that screenshots the current component across its states, plus the target when matching two implementations. No baseline, no parity claim. A blocking prerequisite, not a follow-up. Give every state a page of its own (a dev-only route that renders the component in that state), list those pages and the sizes in the harness config so every compare is the same, and save a named baseline (for example `parity-baseline`), in light and dark when the component themes. When the target is the main checkout's running implementation, main is the baseline. Use the project's own harness, or Playwright `toHaveScreenshot` with zero tolerance, and commit the baseline images. See your adapter for a built-in visual diff.
2. Anti-shortcut clauses, stated and held: no harness modifications, no baseline tampering, no component restructuring to make a diff pass. A new mask or a looser threshold is a harness modification. Masks are only for content that changes between two loads of the same page, set before the baseline is taken. If the baseline looks wrong, stop and ask, don't edit it.
3. Migrate one component at a time. Parallelize across worktrees, one owner per component (the **Separate Before Serializing Shared State** principle, `principles/separate-before-serializing-shared-state.md`). Give each component a writing helper in its own worktree, each with its own dev server so the shots don't collide. Shared primitives migrate first as a blocking phase.
4. Verify each component against its baseline via image diff on the matching surface. A nonzero diff is a fail. Investigate the pixel delta. The diff must report no change at every size for every state page. Crop the changed region of any changed shot to find the delta, and show the user the same visual diff with its heatmap. Repeat per component until the diff is zero (a loop, if your agent has one; see your adapter).
5. Keep a parity table, one row per component (component, states, sizes, result, largest delta, note). Publish it as a CSV artifact with a `status` column of pass or fail and rewrite it as components land, else a markdown table in the reply.
6. Run **Opening a PR** (`playbooks/opening-a-pr.md`) per component or per safe batch. Put the component's diff result in its PR.

**Reply:** components migrated, the diff result for each (the parity table, and the visual diff for any that changed), the baseline harness location, what's left.
