### Release

**You own the release from green main to a verified, published artifact.** The repo's own release skill is the spec. This playbook fills its gaps and never overrides it.

For "release", "cut vX.Y.Z", "tag", "retag", "check the release". Tagging and publishing are outward-facing. Do them when the user asked for this release. Otherwise prepare everything and ask.

1. **Find the repo's release process.** Look for a release skill (`.claude/skills/release/SKILL.md`), then `RELEASING.md`, `CONTRIBUTING.md`, the release workflow under `.github/workflows/`, and the memories. When a release skill exists, read it in full and follow it step by step. Where it and this playbook differ, it wins. Note who may push tags. When a ruleset blocks the agent, prepare everything and hand the user the exact commands.
2. **Confirm CI is green on HEAD of main.** `git fetch origin`, then `gh run list --branch main --limit 5` and `gh run view <id>` for the run on `origin/main`'s SHA. Pending means wait (`gh run watch <id> --exit-status` in a background Bash, then end your turn). Red means no release. Fix it through **Bug fix** first, or ask whether to ship anyway when the failure is known and unrelated.
3. **Smoke the built artifact for real.** Build what users will run (the app bundle, the binary, the package) from that SHA and run it. Drive its main flow on the real surface. A desktop app gets launched and clicked through (in a berth worktree pane, or the **berth-browser** skill for its web view). A CLI runs its main commands. Screenshot it or paste the output. Tests passing is not a smoke test. Memories may name the exact smoke steps. Follow them.
4. **Pick the version and write the changelog.** Choose the bump from what's in `## Unreleased` (a fix is patch, a feature is minor unless the repo says otherwise). Move every Unreleased bullet under the new version heading in plain words. Bump every file that carries the version (manifests, lockfiles, app config) so they agree. `git grep` for the old version to catch stragglers. Commit as the repo's convention says (often `release: vX.Y.Z`), always through a PR. Never push the release commit to main directly.
5. **Tag.** State the action in one line first ("tagging v1.4.0 on <sha> to publish the release"). Then, once the release PR has merged, create an annotated tag on that exact SHA on main and push the tag, using the repo's commands. Never tag a SHA whose CI you haven't seen green.
6. **Watch the release workflow.** Find the run (`gh run list --workflow <release.yml> --limit 3`) and `gh run watch <id> --exit-status` in a background Bash, or the `Monitor` tool. End your turn while it runs. A slow job is not a failed job, so don't cancel a healthy run. Cancel only superseded runs for an old tag.
7. **On failure, fix forward.** Read the failing job's log and classify it. Flake or infrastructure gets one rerun of the failed jobs. An identical second failure is real. A real failure gets a fix on main through a PR, with CI green again. Retag only when it is safe, meaning nothing was published (a draft at most, per the repo's skill) and no user could have pulled the tag. Moving a tag is a force push of a tag. Pause and ask before it, unless the user explicitly said to retag. Then delete the draft and move the tag the way the repo's skill says. Once anything is published, never move the tag. Cut the next patch version instead.
8. **Verify what users get.** The release is marked latest. Every expected asset is attached. The update feed or package index reports the new version (`curl` the feed, `npm view`, or the repo's own check). Download one asset and check it the way the repo's skill says (signature, notarization, checksum, that it launches). Install or update through the path users take, when that can be done safely.
9. **Run the post-release steps.** Do what the repo's skill or the memories name after a release (pointing local tooling back at the released build, upgrading boxes, announcing). An announcement to other people is outward-facing. Draft it and ask unless the user asked you to post it.
10. **Keep the release table.** One artifact with the version, the commit SHA, the CI run on main, the smoke-test evidence, the release workflow run and its result, each verification check with pass/fail and its command, and links to the release, the changelog section and the feed. Inside berth, the **berth-artifacts** skill (Markdown or CSV). Outside berth, the `Artifact` tool or a markdown table in the reply. Update it as each step lands, so a failed run shows where it stopped.

**Reply:** the version and its release link, the commit, the CI and release-run results, the smoke-test evidence, each verification with its result, any retag or fix-forward and why, post-release steps done or pending, and the release table link. If the agent couldn't push the tag, the exact commands for the user.
