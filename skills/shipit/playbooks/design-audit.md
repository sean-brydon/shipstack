### Design audit

**You own the bar. Every axis at 8/10 or better, in light and dark, at every size, proven by screenshots.** Or an honest note saying which axis fell short and why. Scores are judgments, so the shots carry the claim.

For "make this look right", "get it to 8/10", "audit the UI", "this looks off", and every new or changed UI before its PR. Pixel-exact equivalence between two implementations is **Visual parity** instead.

1. **Scope the audit.** List the screens or components, the routes that show them, and the states each needs (default, empty, loading, error, long content, hover and focus, disabled, a narrow window). Desktop apps add the window chrome. A state the app can't reach on its own gets a dev-only route or a fixture (synthetic, "acme" data).
2. **Load the house style and its constraints.** Find the project's design system and use its primitives and tokens. Where the project uses coss-ui (a `components.json` with an `@coss` registry, or coss-ui components in the tree), every control is a coss-ui component and every color, radius, shadow and spacing value is a token. Grep the scope for hand-rolled styles (raw hex, arbitrary values like `rounded-[7px]` or `p-[13px]`, one-off shadows, native controls where a primitive exists) and list each hit. Read the saved memories for style decisions. They are constraints, not suggestions. A memory that keeps input borders subtle means the audit never "fixes" their contrast upward.
3. **State the rubric before the first shot.** Score each axis 0-10 and write what an 8 looks like for this UI:
   - **Hierarchy.** The eye lands on the primary action and the most important content first.
   - **Spacing and radius.** One spacing scale and one radius family, used consistently. No near-misses (12px next to 14px).
   - **Contrast and legibility.** Text and icons readable in both themes, within the saved style memories.
   - **Alignment.** Shared edges and baselines line up. In a desktop app the title bar content is centered on the same line as the window controls.
   - **States.** Every state from step 1 exists and looks designed, not defaulted.
   - **Fidelity to the design system.** Primitives and tokens only. Zero hand-rolled hits from step 2.

   Optional references set the bar, not the look. When design-reference tools are available (a screen library or a design canvas), pull two or three comparable screens and link them in the artifact.
4. **Round 0 is the baseline.** Screenshot every screen and state in light and dark at phone, tablet and desktop. Drive the real surface for states that need a click, and resize the window per size and toggle the theme (see your adapter for the browser and screenshot tools; use the project's own browser tests if it has them). Where your environment can save a named baseline set of shots, save this one as `audit-r0`. Read every image yourself. A shot of a spinner, an error page or the wrong theme is retaken, not scored.
5. **Score and name the defects.** Score each screen per axis, in each theme. Every score under 8 names its defect concretely (the element, what's wrong, the token or primitive that fixes it). "Feels cramped" is not a defect. "Card body uses `p-3` while siblings use `p-4`" is.
6. **Fix, highest impact first.** Order the defect list by how much each lifts the lowest axis. Fix with the design system's primitives and tokens. Never add a hand-rolled style to fix a hand-rolled style. A fix that needs a new token or a new primitive is a design decision, so propose it in the artifact rather than inventing it. Shared components touched by a fix get checked on every screen that uses them.
7. **Rescreen and append the round.** Retake the same matrix. Where a visual diff against a named baseline is available, compare against the previous round (`audit-r<N-1>`) in both themes to show what each fix moved and to catch drift elsewhere, then save the new baseline as `audit-r<N>`. Without it, pair the shots by hand. Append the round to the artifact with the shots, the scores, the fixes applied, and the delta per axis.
8. **Stop at the bar or the cap.** Stop when every axis on every screen scores 8 or better in both themes, or after 5 rounds (or the user's cap). Before you claim the bar, give a fresh helper the final shots and the rubric, without your scores, and ask it to score them and report gaps, not style preferences. Where you differ by 2 or more on an axis, look again and settle it in the artifact. At the cap, write the honest note with the axes still under 8, why, and what it would take (a decision, a new primitive, a redesign).
9. **Keep it in one artifact.** Every round's shots (light and dark, three sizes), the rubric, the score table, and a chart of each axis's score by round. Make it an HTML page, rewritten each round so the user watches it fill (see your adapter for how to publish it; load the artifact-design and dataviz skills if your environment has them). Name the commit and URL each round was shot from.
10. **Close out.** Run the visual diff against main for the whole scope in both themes (paired shots by hand where no diff tool exists), build the proof pack (`references/proof-pack.md`) with the final score in it, then run **Opening a PR** (`playbooks/opening-a-pr.md`).

**Reply:** the final score per axis (and per screen where they differ), the rounds it took, the biggest fixes, anything still under 8 with the reason, the artifact link, and the visual diff against main. Name any saved style memory that ruled out a fix.
