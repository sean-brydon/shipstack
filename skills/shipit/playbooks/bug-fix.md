### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead. Pick each subagent's `effort` for the job, per the Subagents section of `~/.claude/skills/shipit/SKILL.md`.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

1. Reproduce it yourself on the matching surface via the control skill (Non-negotiables), even when a debug or instrumentation protocol says to ask the user to reproduce. For a page, that is the **berth-browser** skill inside a berth worktree (`berthd browser open`, drive it, `berthd browser console`, `berthd browser shot`), else the **claude-in-chrome** skill. For a CLI or TUI, drive it with Bash, or tmux (`tmux new -d`, `send-keys`, `capture-pane`) when it is interactive. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires. Save the failing output, and for a visual bug the screenshot, as the before half of the proof.
2. Binary-search the cause. Form the candidate hypotheses, then rule them out until one survives. Seed them with the **how** skill (`~/.claude/skills/how/SKILL.md`) over the affected subsystem and the **why** skill (`~/.claude/skills/why/SKILL.md`) for regression history. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. Drive a long or stubborn hunt with Claude Code's `/loop`. Keep the hunt as a table, one row per hypothesis (hypothesis, the split, the evidence, ruled out or surviving). Past a handful of rows, make it an artifact with the **berth-artifacts** skill (a `.csv`, rewritten as rows land), or a markdown table outside berth. Confirm the surviving *mechanism* with runtime evidence before the step-3 architect/interrogate fan-out.
3. Plan the fix. If it crosses a function boundary, run the **architect** skill (`~/.claude/skills/architect/SKILL.md`) first. Delegate implementation to a subagent using your configured bug-fix model (the `bug-fix` line in `~/.claude/shipit/models.md`, default `sonnet`) with a specific scope.
4. Verify on the same surface. The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence. For a visual bug, take the after screenshot at the same size and state as the before. Inside berth, run the **berth-visual-diff** skill (`berthd shots compare`) so the user sees before and after with a slider and a heatmap, and nothing else moved.
5. Stage the commits so the failing repro lands before the fix in git history. See the **tdd** skill (`~/.claude/skills/tdd/SKILL.md`) for the failing-test-first cadence when the bug has a cheap local test path. Skip it when the test would be expensive, integration-heavy, or unclear.
   This is the canonical **Sequence Work into Verifiable Units** principle (`~/.claude/skills/shipit/principles/sequence-verifiable-units.md`), the failing test first and the fix on top.
6. Run **Opening a PR** (`~/.claude/skills/shipit/playbooks/opening-a-pr.md`).

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim. For a visual bug, link the before and after screenshots or the visual diff. Link the hypothesis table when you made one.
