**What it does.** Lays out real options with a recommendation, then stops for your pick. No code, no branch.

**Say something like.** "I want to…", "what if we…", "help me plan", "no code"

<details className="ss-full">
<summary>Full instructions (what the agent reads)</summary>

**You own the options and the recommendation. The user owns the pick.** No code, no branch, no scaffold. The deliverable is a decision the user can make in one reply.

For "I want to…", "what if we…", "I wonder if…", "help me plan", "no code, just ideas". The one playbook where the **Never Block on the Human** principle ([`~/.claude/skills/shipit/principles/never-block-on-the-human.md`](/principles/never-block-on-the-human)) inverts. You stop and wait, by design. Exploring is cheap here. Building the wrong thing is not.

1. **Play the goal back in one sentence.** Who it is for, what changes for them, and how you'd know it worked. Put that sentence at the top of the artifact. If you can't write it, the first question in step 9 is the one that lets you.
2. **Check what's already decided.** Read the memories Claude Code loaded, the repo's AGENTS.md or CLAUDE.md, and any design notes or past PRs on the topic (`git log --grep`, `gh pr list --search`). A saved rejection or a parked idea is a constraint. It never comes back as an option. If the goal seems to need it, say so plainly and design around it.
3. **Explore what exists.** Read the code the idea touches, enough to know what's cheap and what's structural. For a subsystem question, run the **how** skill ([`~/.claude/skills/how/SKILL.md`](/skills/how)). When the ground is broad (several subsystems, or how other products do it), fan out `Explore` subagents or the **swarm** skill ([`~/.claude/skills/swarm/SKILL.md`](/skills/swarm)) and keep only their conclusions (the **Guard the Context Window** principle, [`~/.claude/skills/shipit/principles/guard-the-context-window.md`](/principles/guard-the-context-window)). When outward prior art dominates, run the **Research** playbook ([`~/.claude/skills/shipit/playbooks/research.md`](/playbooks/research)) first and feed its matrix in.
4. **Attack the premise before multiplying it.** Ask whether an existing feature already covers the need, whether a smaller version delivers most of the value, and whether removing something beats adding something (the **Subtract Before You Add** principle, [`~/.claude/skills/shipit/principles/subtract-before-you-add.md`](/principles/subtract-before-you-add)). "Don't build it" and "cut X instead" are real options when they are true.
5. **Draft 2-4 real options that differ in kind, not degree.** Each gets a letter (A, B, C, D) and these fields:
   - **What it is.** One or two sentences.
   - **What the user sees.** The experience, not the implementation.
   - **Effort.** S, M or L, and what drives it (new data shape, new surface, migration).
   - **Risks.** What could go wrong, what it rules out later, what it costs to undo.
   - **Evidence.** The file, the prior art or the measurement behind each claim, labeled measured, inferred or guess.

   Don't pad to four. Two strong options beat four with filler. Variants of one idea are one option (the **Exhaust the Design Space** principle, [`~/.claude/skills/shipit/principles/exhaust-the-design-space.md`](/principles/exhaust-the-design-space)).
6. **Push back on gimmicks.** Apply the **Experience First** principle ([`~/.claude/skills/shipit/principles/experience-first.md`](/principles/experience-first)). An option that is clever but doesn't make the product better for its user gets called gimmicky in the artifact, with the reason. If that's the user's own idea, say so anyway. Agreement is not the default.
7. **Score and recommend.** State the rubric before scoring: user value, fit with the product, effort, risk, reversibility. Score each option 1-5 per axis with a one-line reason. Lead with the recommendation, why, and what would change your mind. A combined option ("C with A's onboarding") is fine when it's genuinely better than either.
8. **Put it in one artifact.** Goal sentence, constraints from step 2, the options table, the scores, the recommendation, the open questions, and sources linked. Inside berth, a Markdown or HTML page with the **berth-artifacts** skill. Outside berth, the `Artifact` tool (load the **artifact-design** skill first). A sketch or diagram per option is worth it when the options are visual or structural (Mermaid for flows). The test is whether the user would rather look at it than read it.
9. **Ask targeted questions.** Use `AskUserQuestion`. The first question is the pick, its options labeled A, B, C with the recommended one first and marked "(recommended)". Add at most two more, and only questions no experiment can settle (product direction, taste, priority). A question you could answer by reading code or running something is yours to answer. Without `AskUserQuestion` (a subagent, a headless run), put the same questions at the end of the reply.
10. **Stop.** End the turn. No code until the user picks.
11. **Fold in the answer.** Combining options ("C and A") is a normal answer. Write the merged option back into the artifact in one paragraph, flag any conflict between the parts, and mark the decision with the date. Then route. A visual or behavioral fork still open goes to **Prototype**. A settled direction goes to **Feature**. The artifact is the brief.

**Reply:** the goal sentence, the options in one line each, the recommendation and why, the artifact link, and the questions. After the pick, the merged decision and the playbook it routes to. Name the principles that changed an option or cut one.
