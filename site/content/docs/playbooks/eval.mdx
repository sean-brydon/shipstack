**What it does.** Runs a blind experiment to test whether a skill, structure or prompt change helps, before it is promoted.

**Say something like.** "did this skill change actually help?"

<details className="ss-full">
<summary>Full instructions (what the agent reads)</summary>

**You own the experiment design. Plan, blind, run, synthesize.**

**Non-negotiables for blinding:**

- No `eval`, `test`, `judge`, `experiment`, `rubric`, `score`, `compare`, `benchmark`, `candidate`, or `arena` in any directory, file, worktree, branch, or prompt the candidate sees.
- The candidate prompt looks like an organic user request. State the goal, not the meta.
- No chain-eliciting cues. Don't ask the candidate to list which skills, principles, or files they applied. Ask for design notes generally and grade chain-following from code shape, not self-report.
- Sanitize directory and slug names. Use project-shaped names a user might pick.
- Don't tell the candidate other candidates exist.
- The judge can know it's judging but sees outputs by sanitized label only, never by model name.
- Comparing two variants: one judge scores both sets in a single pass on one scale, blind to which set each came from.

**Steps:**

1. **Frame.** State what variant is under test and what behavior counts as success. Write the rubric (3-6 concrete criteria) for the judge only. Hold it back from candidates. Also list the files a candidate following the chain should open (the skills, principles, or references the variant routes to). That list grades step 6.
2. **Set up sanitized environments.** Per-candidate working dir with the variant in place. Plant any context an organic task would have: a project skeleton, the skills the candidate would naturally read. Give each candidate its own worktree or directory, named like a real branch, outside this repo (your adapter's "a candidate in its own directory" row says how to start one there).
3. **Author one organic prompt.** What a user would type. No leakage of what's being measured.
4. **Spawn N parallel candidates** on different models per the **arena** skill's Phase B (`<skills>/arena/SKILL.md`). Each works in its own sanitized dir. Same prompt to each. Pick each helper's effort for the job, per the Helpers section of the **shipit** skill (`<skills>/shipit/SKILL.md`). Different models means different model families, from the arena runners and any extra family the user configured in `models.md`. Never start a candidate as a shipit writing helper. A writing helper reads the shipit router first, which leaks the setup and changes what you measure. Start each one the way your adapter's "a candidate in its own directory" row says, from its own sanitized dir so its transcript lands under that dir, in the background. End your turn. Each reports back when it finishes.
5. **Spawn one blinded judge** on a different model family per the **arena** skill's Phase C. Judge sees outputs by sanitized label and the rubric, never a model name. Have it return a score per criterion per label, not only a verdict.
6. **Verify the chain from transcripts, not self-report.** Read the session transcripts of the candidates you started (see your adapter for where they live and what shape they have). A helper's transcript may sit under its parent session, and a candidate run in its own dir or worktree has its own folder. Read only the transcripts of the candidates you started. Do not glob across every project's transcripts. That crosses workspace boundaries and reads private chats from unrelated projects. Look at which files each candidate actually opened (its read, search, and shell tool calls). Grade chain-following from the files it really read plus the shape of the code, never from the candidate's own claims.
7. **Read every candidate output yourself** end to end. Compare to the judge's verdict. Disagreement means a model is biased or the rubric is ambiguous. Synthesize.
8. **Show the results.** Two artifacts. The judge's scores as a chart (a heatmap with the criterion on one axis, the sanitized label on the other and the score as the cell value, or a grouped bar when there are few criteria), and the chain matrix from step 6 as a CSV (label, each expected file opened yes or no, files opened that were not expected). Add the model behind each label only after judging is done. Publish them as artifacts (load the dataviz and artifact-design skills first if your environment has them), or as markdown tables in the reply. Each names the prompt, the rubric, and the run it came from.

**Reply:** variant under test, rubric, per-candidate notes, judge's verdict, the score chart and chain matrix, your synthesis, and a recommendation for whether to promote the variant.
