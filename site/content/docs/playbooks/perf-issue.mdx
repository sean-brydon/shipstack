**What it does.** Traces a measured slowness and improves it against a baseline. Every fix is tied to a measurement.

**Say something like.** "… is slow", "trace it"

<details className="ss-full">
<summary>Full instructions (what the agent reads)</summary>

**You own the measurement story. Plan, review, verify the numbers.** Tie every fix to a measurement, don't read source instead of measuring.

1. Capture a baseline trace via the matching control skill (Non-negotiables). For a page inside a berth worktree, the **berth-browser** skill drives it (`berthd browser eval` reads `performance` entries), else the **claude-in-chrome** skill. For a CLI, server, or script, time it with Bash. Vet the baseline, and each later number, with the **benchmark-checklist** skill ([`~/.claude/skills/benchmark-checklist/SKILL.md`](/skills/benchmark-checklist)). Record the exact command, the workload, the machine, and N, so anyone can rerun it.
2. Run the **how** skill ([`~/.claude/skills/how/SKILL.md`](/skills/how)) to ground hypotheses. Don't claim a perf ceiling without running it first.
   Try the performance mantras in order, cheapest first:
   1. Don't do it. Stop work whose result nothing uses rather than cheapening it.
   2. Do it, but don't do it again.
   3. Do it less.
   4. Do it later.
   5. Do it when they're not looking.
   6. Do it concurrently.
   7. Do it cheaper.

   When an earlier mantra meets the target, stop.
3. Plan the fix from the trace. If it crosses a function boundary, run the **architect** skill ([`~/.claude/skills/architect/SKILL.md`](/skills/architect)) first. Delegate implementation to a subagent using your configured perf-issue model (the `perf-issue` line in `~/.claude/shipit/models.md`, default `sonnet`). Pick each subagent's `effort` for the job, per the Subagents section of [`~/.claude/skills/shipit/SKILL.md`](/skills/shipit). Review the diff. Capture a post-fix trace with the same command, workload, and N.
   Apply the **Sequence Work into Verifiable Units** principle ([`~/.claude/skills/shipit/principles/sequence-verifiable-units.md`](/principles/sequence-verifiable-units)), verifying each attempt before trying the next.
4. Parse and compare the artifacts (JSON to sqlite, diff). "Inconclusive" or wrong-surface is not a pass. Flag it.
5. Chart the result. Inside berth, write a `berth.chart` bar chart (before in `muted`, after in a series colour, `better: "lower"` or `"higher"`, `units` set, the command and N in `subtitle` or `notes`) and register it with the **berth-artifacts** skill. Add a table of the top frames or phases before and after when the trace shows where the time moved. Outside berth, publish the chart with the `Artifact` tool (load the **dataviz** and **artifact-design** skills first), or put a markdown table of baseline, post-fix, and delta in the reply.
6. Cite the measurement in the PR: the numbers, the command, N, and the chart or table.
7. Run **Opening a PR** ([`~/.claude/skills/shipit/playbooks/opening-a-pr.md`](/playbooks/opening-a-pr)).

For sustained improvement against a metric rather than a one-off fix, use the Hillclimb playbook ([`~/.claude/skills/shipit/playbooks/hillclimb.md`](/playbooks/hillclimb)).

**Reply:** baseline number, post-fix number, delta, artifact path, and the chart or table from step 5.
