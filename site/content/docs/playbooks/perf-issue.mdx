**What it does.** Traces a measured slowness and improves it against a baseline. Every fix is tied to a measurement.

**Say something like.** "… is slow", "trace it"

<details className="ss-full">
<summary>Full instructions (what the agent reads)</summary>

**You own the measurement story. Plan, review, verify the numbers.** Tie every fix to a measurement, don't read source instead of measuring.

1. Capture a baseline trace on the matching surface (Non-negotiables). For a page, drive the real surface and read the browser's `performance` entries (see your adapter). For a CLI, server, or script, time it from the shell. Vet the baseline, and each later number, with the **benchmark-checklist** skill (`<skills>/benchmark-checklist/SKILL.md`). Record the exact command, the workload, the machine, and N, so anyone can rerun it.
2. Run the **how** skill (`<skills>/how/SKILL.md`) to ground hypotheses. Don't claim a perf ceiling without running it first.
   Try the performance mantras in order, cheapest first:
   1. Don't do it. Stop work whose result nothing uses rather than cheapening it.
   2. Do it, but don't do it again.
   3. Do it less.
   4. Do it later.
   5. Do it when they're not looking.
   6. Do it concurrently.
   7. Do it cheaper.

   When an earlier mantra meets the target, stop.
3. Plan the fix from the trace. If it crosses a function boundary, run the **architect** skill (`<skills>/architect/SKILL.md`) first. Delegate implementation to a writing helper in its own worktree, on the `code` role's model. Pick each helper's effort for the job, per the Helpers section of the **shipit** skill. Review the diff. Capture a post-fix trace with the same command, workload, and N.
   Apply the **Sequence Work into Verifiable Units** principle ([`principles/sequence-verifiable-units.md`](/principles/sequence-verifiable-units)), verifying each attempt before trying the next.
4. Parse and compare the artifacts (JSON to sqlite, diff). "Inconclusive" or wrong-surface is not a pass. Flag it.
5. Chart the result as an artifact. Make a bar chart with before muted and after in a series colour, the direction of better stated (lower or higher), units set, and the command and N in the subtitle or notes. Add a table of the top frames or phases before and after when the trace shows where the time moved. Load the **dataviz** skill for the chart if your environment has it. If you cannot publish an artifact, put a markdown table of baseline, post-fix, and delta in the reply.
6. Cite the measurement in the PR: the numbers, the command, N, and the chart or table.
7. Run **Opening a PR** ([`playbooks/opening-a-pr.md`](/playbooks/opening-a-pr)).

For sustained improvement against a metric rather than a one-off fix, use the Hillclimb playbook ([`playbooks/hillclimb.md`](/playbooks/hillclimb)).

**Reply:** baseline number, post-fix number, delta, artifact path, and the chart or table from step 5.
