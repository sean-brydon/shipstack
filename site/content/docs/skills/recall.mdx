**What it does.** Rebuilds your recent context on a topic from your own transcripts, project memory, live state and past fixes.

**Use when.** Starting or resuming work. "Where did I leave off on X?"

**Skip when.** Catching up on this chat only (use ketchup).

```text
/recall my work on phone pairing this week
```

**You get.** A short current-state brief: done, open, decided, next.

**In /shipit.** Session pickup.

**Before you start or resume work, you rebuild the user's recent working context and hand back a tight capsule of where things stand now and what to do next.**

Keep it tight and on-topic. Read only what the in-scope threads need, then stop.

Your context lives in two records. Your own chat history holds what you did and decided. The shared record holds everything that happened around the same code under other names: the symptoms users keep reporting, the fixes that shipped and got reverted, the errors still firing in prod. That second record is what the **why** skill searches, across source control, the issue tracker, chat and issue channels, long-form docs, and error tracking. A feature with a long bug tail keeps most of its story there, so don't reconstruct it from your transcripts alone.

The session transcripts are your chat history on disk. Your adapter says where they live, what a record looks like, and how to pull out the human's own turns. Saved memories are the project's remembered corrections and preferences. Read your adapter on both before you hand out slices.

1. Classify, then route. One specific prior chat to resume is the Session pickup playbook ([`playbooks/session-pickup.md`](/playbooks/session-pickup) in the shipit skill), not this. Turning habits into a durable skill is the **automate-me** skill. A human-readable summary of your work is a different task. Recall loads working context across recent chats before you act. If the user already gave you a full state capsule (paths, branch, the change), use it and skip the mining.
2. Lock the scope before searching. Pin the window ("recent" is a real range, default the last 7 days), the topic if named, and the workspace (default the active project, plus this repo's other worktrees from `git worktree list` when the user means the repo. Never read another project's transcripts without being asked). State the scope back. Never quietly turn "all" into "recent N".
3. Fan out across your chat history. Spawn parallel read-only helpers, using the `recall readers` model from the shipit models file (the reading role's model, or a stronger one when the slices are dense and the line is unset), each taking a slice of the corpus and the transcript notes from your adapter. Tell every helper to order candidates by real modification time and never by file name, search for the topic first (chat titles and the human turns are the cheap places to look) and then read only the matching chats and only their relevant regions, and skip the current chat, helpers' own transcripts, and obvious noise (eval and test chats). Each returns the same schema, one block per chat: topic, the user's goal, decisions, open threads, struggles and corrections, and artifacts (PRs, tickets, branches), each citing the chat's session id. For one or two chats, skip the fan-out and search directly. The raw transcripts stay in the helpers. The main thread gets only their findings. Set each helper's effort for the job, per the Helpers section of the **shipit** skill.
4. Read the saved memories yourself. Open the memory index and only the memories whose index line touches the topic. A memory is a correction the user already made once. Fold the relevant ones into the brief as standing rules, cited by name.
5. Sweep the shared record whenever the topic names a feature, file, subsystem, area, or bug. This is the default, not a judgment call, and "my work on X" does not exempt it. Hand it to the **why** skill's source investigators, but steer their question from "why was this built this way" to "what's the current state, what's been tried and didn't hold, and what are users still reporting". Reuse its per-source playbooks, run the investigators in parallel with the chat-history mining, and inherit its posture: one investigator per source, null results are findings, skip an unavailable source and say so. Fold what comes back into the brief. Skip this step only for pure activity recall with no named target ("what did I do this week"), where your own history and live state are the entire answer.
6. Verify against live state. Take the PRs, branches, and tickets that the mining and the sweep surfaced and check them with `git` and `gh`. If you use an orchestration tool, it may also show which worktrees and agents still hold the work (see your adapter). When the answer hinges on what an agent actually did (the tools it ran, files it read, errors it hit), read the full transcript and any helper transcripts, not just a helper's summary.
7. Write the brief to the contract below. Group by thread. Stay on the named topic.

## Output contract

Lead with the capsule, then the thread status, then the problems, then the next move. Deeper detail goes below or gets cut.

- **Capsule.** At most 5 bullets. What this work is and where it stands overall.
- **Threads.** One line each, prefixed with exactly one status tag: `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[verified, uncommitted]`, `[reverted #N]`, or `[planned, not started]`. A thread with no tag is not done yet, so tag it.
- **Problems.** At most 5, the recurring ones. Include the symptoms users keep reporting and any fix that shipped and was reverted, so the next attempt starts where the last one failed.
- **Next move.** The single most useful next action, concrete.

When the threads run past about 8, also show them as a table artifact (thread, status, PR or branch, last touched, source) so the user can scan it, as an artifact if you can make one, else a markdown table in the reply. Say where each row came from.

An adjacent feature or ticket stays out unless it blocks this one. When the capsule and thread lines outgrow a screen, cut detail before you cut threads. Write the brief through the **unslop** skill, cite chat findings by session id and shared-record findings by their source (PR #, ticket ID, chat permalink, error-tracker issue), cite memories by name, and sanitize private context before any public output.

**Reply:** the brief, to the contract above.
