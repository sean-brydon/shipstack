**What it does.** Generates a project-local verify skill that drives your app like a user and saves proof a PR can embed.

**Use when.** A project has no scripted way to prove UI, CLI or service behavior.

```text
/create-verification-skill for the Shipyard app
```

**You get.** A .claude/skills/verify-&lt;app>/ skill with a feature map.

**In /shipit.** setup-shipit offers it.

<summary>Full instructions (what the agent reads)</summary>

Every serious project needs a scripted way to drive the real app and prove behavior: launch it, exercise a feature the way a user would, and capture evidence. This skill generates that as a project-local skill (`verify-<app>/` in the project's skills folder, which your adapter names) tailored to the repo. You write the generator's output for the next agent, not for a human. It will be read cold, mid-task, by an agent that has never seen the app.

## 1. Interview the repo, not the user

Answer these from the codebase and only ask the user what you cannot observe:

- **Surface.** What does a user actually touch? A web UI, a CLI/TUI, a desktop app, an API, a mobile app, a library? A repo can have several. Pick the primary one and note the rest.
- **Run.** How does the app start locally? Prefer the repo's own documented dev command (package scripts, Makefile, README quickstart). Note ports, env vars, seed data, auth. If your orchestration tool keeps a per-repo config (see your adapter), read it too. It may name the dev server's command, port, env, services and dev users.
- **Drive.** How can an agent interact with it programmatically? Existing harnesses first: Playwright/Cypress specs, expect scripts, PTY helpers, curl-able endpoints, a debug port. Only then pick a generic recipe:
  - A web UI: the browser or CLI driver the environment has (your adapter lists them). Prefer the project's own Playwright if it has one. If the driver controls the user's real browser, the generated skill opens its own tab and never touches the user's other tabs or logged-in sessions. If the environment can also run a visual diff against main across widths, note it for the Evidence section.
  - Electron or a desktop app: its debug port (CDP) through the project's Playwright.
  - A CLI or TUI: Bash for one-shot commands, a tmux session per drive (`tmux new -d`, `send-keys`, `capture-pane`) for interactive ones.
  - A service: plain HTTP with `curl`.
- **Observe.** What evidence can be captured? Screenshots, terminal transcripts, response bodies, logs, exit codes, DB state. For a UI with a dark theme, the evidence is a screenshot in light and in dark.
- **Isolate.** Can two instances run side by side (ports, data dirs, profiles)? If each worktree already has its own port and env, say which of those the skill relies on. If instances can't run side by side, say so in the generated skill. Refusing to double-drive a shared instance beats corrupting the user's session.

If the checkout doesn't build or start as-is, fix that first (or report it precisely) before generating. A skill written against a broken base teaches wrong steps. When an irrelevant missing asset blocks startup (a static dir the API never serves, a sample config), the generated skill may create it, clearly marked as verification scaffolding, and remove it in cleanup.

## 2. Generate the skill

Write `verify-<app>/SKILL.md` in the project's skills folder with YAML frontmatter (`name: verify-<app>` and a `description` that names the app, the surface, and when to reach for it; without frontmatter the skill never registers) and these sections, each grounded in what the interview actually found (no placeholders left):

- **Launch.** The exact command that starts the app for verification, and how to tell it's ready (a log line, a prompt). Launch must reach a usable state from an empty data dir, including any migrations and seed data. Ready means usable, not just that a process answers. A database health check can pass while its init scripts are still running. Include teardown. For a short-lived CLI or TUI there is no server to keep alive. Launch means build the binary (or install deps) once, then start each drive in its own isolated PTY or tmux session. If your environment assigns the worktree a port, launch on it so the agent's browser and the user's preview see the same server.
- **Doctor.** One read-only check that answers "is this instance worth driving?": process up, right version/build, port owned by us, auth valid. An agent runs this first whenever anything looks off.
- **Drive.** The harness recipe with real selectors/commands from this repo, not examples. Prefer stable handles (ARIA labels, data attributes, prompt strings, route paths) over coordinates and tab order. If the driver addresses elements by refs from a page snapshot, name the accessible name each ref belongs to, since refs change when the page navigates.
- **Evidence.** What to capture for a proof and where it goes. State the proof standards: exercise the real user path, not internal setters or test-only endpoints; capture the action and the resulting state, not just the final screen; verify side effects (files written, rows inserted, messages sent) alongside what's visible; mocks only where a production boundary already isolates the external system. When the safe path is a dry-run or test mode, verify what it actually skips by observing (files, network, git refs) rather than trusting its name. Some dry-runs still touch the network or open a browser. For UI, the proof is screenshots in light and dark, taken with the driver's color-scheme emulation or the app's own theme switch. Name the folder the proof lands in, outside anything cleanup deletes, and say how a PR embeds it: the repo's convention for proof images if it has one, otherwise list the files in the reply for the human to attach. A visual diff against main, if your environment can make one, is already an artifact the user can open.
- **Cleanup.** How to tear down instances the run created. Never kill by process name. Kill what you started. Cleanup removes instances and scratch state, never the evidence. Proof artifacts survive the teardown, in a location the skill names.
- **Helpers.** Any script the skill ships is executable and its invocation is shown in the skill body. A helper the reader has to reverse-engineer is not a helper.

## 3. Seed the feature map

Create `verify-<app>/features/README.md` plus one file per user-facing feature you can identify (aim for the top 3-5 to start, from routes, commands, menus, or docs). Follow the shape in [`references/feature-map-example/`](https://github.com/sean-brydon/shipstack/blob/main/skills/create-verification-skill/references/feature-map-example/), with a README index and one file per feature. Each file answers, from the user's point of view: what the feature is, how to reach it, how to drive it with the harness, and what observable end state proves it works. The four H2s are `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, and `Gotchas`. If the seed data lacks a precondition that a journey needs, the journey reports a failure and the reason goes in that feature's `Gotchas`. Never weaken the journey to make it pass. The map is the repo's maintained verification source. A proof that drives one convenient entry point is incomplete when the map lists others.

## 4. Prove the generated skill before handing it over

Run its own instructions end to end once: launch, doctor, drive ONE mapped feature (one is enough; the map exists so later runs can cover the rest), capture evidence, clean up. After cleanup, confirm the evidence still exists at the named location. A cleanup that eats the proof fails this step. Look at every screenshot before you call it proof: a blank page, a half-loaded view, or the wrong theme is not evidence. Fix what fails, and run the generated cleanup after every failed iteration too, so broken attempts don't strand processes and ports. A generated skill that was never executed is a draft, not a deliverable. If you proved it in a stand-in for the real target (a container in place of a fresh VM, a local stack in place of a remote one, a laptop in place of a remote box), list every setup step the stand-in did that the target will not. Those steps stay unverified until a run on the real target covers them.

## 5. Offer the maintenance loop

Point the user at `/maintain-verification-skill` for keeping the map honest as the app changes. Suggest a cadence only if they ask.

**Reply:** the generated skill's path, the surface and harness it drives, the feature it proved end to end, and the proof itself (the screenshots or transcript, linked from where they landed).
